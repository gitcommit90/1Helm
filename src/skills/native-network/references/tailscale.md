# Native Tailscale lifecycle

Use `native_network` operations status, tailscale_status, tailscale_connect, and tailscale_disconnect. This is native network membership for this channel's 1HC computer, not a Composio integration or a management API credential.

Connect starts a supported interactive Tailscale login. The human opens the login link in Settings → Connected accounts → Computer connections and approves this 1HC computer joining their tailnet. Explain that this is the agent's computer, not their Mac/phone. The platform gives it a recognizable `1hc-…` device name. Never solicit API keys, reusable enrollment keys or passwords. The model does not receive the authentication URL, approve it, or copy it into chat/history.

Check actual state after the person approves. Structured states distinguish disconnected, awaiting_user_approval, joining, connected, offline/reconnecting, expired/revoked, and error. A login URL or running process is not proof of membership. Only confirmed authenticated membership with an assigned device identity/address means joined. Use explicit status checks; do not start unbounded polling or duplicate login flows.

Call status before saying the computer is either joined or not signed in, even if older chat/memory says otherwise. `verified: false` means current membership is unverified; `checked_at` records the reported observation, not a permanent grant. A sleeping or not-yet-started Tailscale client can retain enrollment: offline/reconnecting or a status timeout is not “disconnected”, expiry or revocation. If checking fails, say that current state could not be checked. Preserve the existing enrollment.

Identify the current enrolled computer by its returned `device_id`, assigned `device_name` and `dns_name`, plus addresses. The requested OS hostname is not a unique identity: after an explicit Disconnect/new Connect, Tailscale may assign a suffix such as `-1` while retaining the older admin record. Do not guess which record is current from the unsuffixed requested name.

Joining does not change the Outbound SSH setting or approve any server. Deny, Ask each time, and Allow trusted servers remain independent of enrollment. Use ordinary public-key SSH to tailnet servers through `ssh_connect` route `tailnet`, then `ssh_session`. Only an explicitly remembered exact server can reconnect automatically in Allow trusted servers; disconnect clears remembered tailnet servers, so re-enrollment does not inherit old trust. Targets do not need to enable Tailscale SSH. The person's existing tailnet policy and target account still control access; do not silently edit ACLs, tags, routes, or server configuration.

The trusted Tailscale client is outbound-only: no inbound services, Tailscale SSH server, Serve, Funnel, advertised subnet routes, exit-node service or default user exit node. Arbitrary agent programs do not get a SOCKS proxy or Tailscale socket. Other tailnet protocols are not exposed by these tools.

Ordinary computer sleep/wake retains the same encrypted identity and reconnects on demand; it is distinct from Disconnect. A successful explicit tailscale_disconnect cancels pending tailnet requests, terminates tailnet SSH sessions, removes local enrollment material and advances a platform-owned invalidation version. It attempts remote logout; inspect the structured remote_logout_confirmed result instead of claiming remote logout succeeded. Local invalidation is guaranteed on success even when remote logout could not be confirmed. Old workspace snapshots cannot restore membership. A new Connect requires fresh human approval. The person can also remove/revoke the device in Tailscale's admin console. Neither local invalidation nor a confirmed logout promises deletion of every remote administrative record. Remote revocation fails closed.

If connected but SSH cannot reach a target, check target name, address, SSH port, tailnet policy, server firewall and installed public key. Tailnet-only targets never silently fall back to public internet. If offline, status may resume the existing identity on demand. For expired/revoked state, explicitly Disconnect to invalidate the old enrollment, then Connect and obtain fresh human approval; retrying Connect alone must not silently replace a previously enrolled identity. Never claim DERP or control connectivity merely because those protocols use HTTPS.

Each SSH prepare/open wakes the saved identity and performs its own bounded membership check; a successful status check is not an SSH grant and the broker may sleep between operations. If status reports connected but an SSH request reports membership unavailable, report the contradictory platform state, check status once, and preserve the enrollment. Do not invent a propagation delay, ask the person to Disconnect/re-enroll, or claim the connection is ready. A private LAN address requires an existing authorized subnet route; enrollment alone does not create that route.
